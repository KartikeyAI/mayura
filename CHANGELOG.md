# Changelog

All notable changes to Mayura are recorded here. The format follows Keep a Changelog, and public versions follow Semantic Versioning.

## [Unreleased]

### Added

- **A model registry.** `createModels({ providers, maxCallCostMicros, prices })` from `mayura` gives every model an id of the form `<provider>/<model>` (`openai/gpt-5.1`), granted as `model:<id>`. A model needs a price, from `prices` or, only with `prices: 'catalog'`, from its provider's dated catalog; and every call has a bound. `registry.model(id, { retry })` calls the same model again after a rate limit, an outage or a timeout (never after the caller cancels or once streamed text was released), charging every attempt. `registry.chain(id, models)` builds a `createModelRouter` over registry models under an id you choose. `registry.list()` shows each model with its price source and catalog date. Providers implement `ModelProvider`; the types `ModelPricing`, `ProviderModelSettings`, `ModelCatalog`, `CatalogModel`, `ModelsOptions`, `ModelOptions`, `ModelChainOptions`, `ModelRegistry` and `RegisteredModel` are exported.
- **`@mayurajs/provider-openai`**, the first `@mayurajs` package: OpenAI models for a model registry (`openai({ apiKey })`, models `openai/<model>`), through the official `openai` SDK and the Responses API. It reads nothing from the environment, turns off the SDK's retries, bounds response sizes, uses strict JSON Schemas, streams output text, and passes the model adapter conformance suite. It exports `catalog`, OpenAI's list prices with their date, used only with `prices: 'catalog'`. Documented in the new Model registry guide.
- **`@mayurajs/provider-anthropic`**: Anthropic Claude models for a model registry (`anthropic({ apiKey })`, models `anthropic/<model>`), through the official `@anthropic-ai/sdk` and the Messages API. It reads nothing from the environment (not `ANTHROPIC_API_KEY`, `ANTHROPIC_AUTH_TOKEN` or `ANTHROPIC_BASE_URL`), turns off the SDK's retries, bounds response sizes, uses strict JSON Schemas, streams output text, and keeps the model's thinking for the next call of a run without ever releasing it. Prompt-cache writes are charged at twice the input rate and cache reads at the full input rate, so a budget never undercounts. Its `catalog` lists Claude Fable 5.1, Opus 5.5, Sonnet 5.5 and Haiku 4.5 at their September 29, 2026 list prices. It passes the model adapter conformance suite.
- **`@mayurajs/provider-google`**: Google Gemini models for a model registry (`google({ apiKey })`, models `google/<model>`), through the official `@google/genai` SDK and the Gemini API. It reads nothing from the environment (not the Gemini or Google API keys, `GOOGLE_GEMINI_BASE_URL` or the Vertex AI settings), turns off the SDK's retries, bounds response sizes, uses strict JSON Schemas, streams output text, and keeps thoughts and thought signatures for the next call of a run without releasing them. Thinking tokens are charged as output and cached input at the full rate. Its `catalog` lists Gemini 3.8 Flash (at the price announced from January 1, 2027, twice today's), 3.5 Flash and Flash-Lite, 3.1 Flash-Lite, 3.1 Pro Preview and 2.5 Pro, with Google's long-context rates above 200K tokens where they apply. It passes the model adapter conformance suite. Two of its packages run installation scripts: the SDK's `preinstall` only prints a line, and `protobufjs`'s `postinstall` only reads `package.json` files to print a version warning. The release checks allow each only while its command, and the SHA-256 of the file it runs, are exactly what was reviewed.
- **`@mayurajs/provider-bedrock`**: Amazon Bedrock models for a model registry (`bedrock({ region, credentials })` or `bedrock({ region, apiKey })`, models `bedrock/<model or inference profile id>`), through the official `@aws-sdk/client-bedrock-runtime` and the Converse API. The region and credentials are options: nothing is read from the environment, AWS config files or instance metadata (a test sets hostile `AWS_*` variables and checks the request is signed with the given credentials, in the given region, at the given endpoint, once). Requests go through a fetch-based handler with bounded response sizes; strict JSON Schemas, streaming, and reasoning kept for the next call of a run but never released. Cache writes are charged at twice the input rate. Its `catalog` lists 18 Claude, Nova, Llama and Mistral models and inference profiles at their us-east-1 list prices, offered only by a provider in us-east-1. It passes the model adapter conformance suite.
- **`@mayurajs/provider-azure`**: Azure OpenAI models for a model registry (`azure({ resource, apiKey })` or `azure({ baseURL, token })` with a Microsoft Entra ID token source called for every request), models `azure/<deployment>`, through the official `openai` SDK and Azure's v1 API. Catalog prices apply only to Global deployments you map to a model (`deployments: { 'prod-chat': { model: 'gpt-5.5', type: 'global' } }`), since deployment names are yours and Data Zone and Regional deployments cost more; the catalog leaves out models whose Azure prices were not yet published. A failing token source reports `authentication` without its error text. It passes the model adapter conformance suite.
- **`@mayurajs/provider-mistral`**: Mistral models for a model registry (`mistral({ apiKey })`, models `mistral/<model>`; `baseURL: 'https://api.eu.mistral.ai'` keeps requests in the EU), through the official `@mistralai/mistralai` SDK and the Chat Completions API. It reads nothing from the environment (not `MISTRAL_API_KEY` or `MISTRAL_DEBUG`, which would make the SDK log every request with its key), turns off the SDK's retries, bounds response sizes, uses strict JSON Schemas, streams output text, and keeps the model's thinking for the next call of a run without releasing it. The SDK's own telemetry, which `MISTRAL_SDK_TELEMETRY` and `MISTRAL_OTLP_TRACES_ENDPOINT` can switch on to export spans of every call, is removed from each client, and the provider refuses to start if a future SDK moves it. Call ids from other providers are renamed to the nine letters and digits Mistral accepts. Its `catalog` lists Mistral Medium 3.5, Large 2512, Small 2603 and Ministral 8B 2512 at their September 29, 2026 list prices; `-latest` aliases are left out, since they move to newer models. It passes the model adapter conformance suite.
- **`@mayurajs/provider-groq`**: Groq models for a model registry (`groq({ apiKey })`, models `groq/<model>` such as `groq/openai/gpt-oss-120b`), through the official `groq-sdk` and Groq's Chat Completions API. It reads nothing from the environment: the SDK merges `GROQ_CUSTOM_HEADERS` into every request's headers, so the provider puts back exactly the headers it was given, and refuses to start if a later SDK changes how it stores them. It turns off the SDK's retries and logging, bounds response sizes, uses strict JSON Schemas, streams output text, and keeps the model's reasoning for the next call of a run without releasing it. Groq refuses a response format beside tools, so with tools the model first answers freely and, once it calls no more tools, one more call without tools asks for the answer in the strict format; the free reply is never streamed, and both calls are charged (found in a live run, where GPT-OSS 20B then passed every tool check). A refusal reports `refused`; a 498 (a flex-tier model over capacity) reports `unavailable`; a tool call or answer the model wrote unparseably (Groq's 400 `tool_use_failed` or `output_parse_failed`) reports `invalid_response`, not `rejected`. Models see images only when `media` says so; images from tool results follow them in one user message. Its `catalog` lists GPT-OSS 120B and 20B and Qwen 3.8 27B at their September 29, 2026 on-demand prices; models sold only through Groq's sales team are left out. It passes the model adapter conformance suite.
- **`@mayurajs/provider-ollama`**: Ollama models for a model registry (`ollama()` for a local server at http://127.0.0.1:11434, or `ollama({ host: 'https://ollama.com', apiKey })` for Ollama's cloud; models `ollama/<model>` such as `ollama/gpt-oss:20b`), through the official `ollama` SDK. `host` is http only on a loopback address and https anywhere else. Nothing is read from the environment or the file system: the provider uses the SDK's browser entry point, whose Node counterpart reads a local file for an image string that names one, and requires an explicit key for ollama.com, where the SDK would otherwise fall back to `OLLAMA_API_KEY`. Each call gets its own client whose transport carries the call's signal, since the SDK passes none for a non-streamed call; error statuses are reported without reading their bodies. JSON Schema structured output and tools: a format constrains every reply to the answer, which leaves no way to call a tool, so with tools the model first answers freely and, once it calls no more tools, one more call without tools asks for the answer in the format (the free reply is never streamed; both calls are charged). Checked live on a local 2B vision model, which then passed structured output, tools, streaming and vision, including an image returned by a tool. Streaming, and `think` for thinking models, whose thinking is kept for the next call of a run and never released. Tool calls get ids unique within the run, since Ollama gives none. Models see PNG or JPEG images only when `media` says so. There is no catalog: local models cost nothing, so each model's price is given, zero or your own. The default time limit is 120 seconds, as a local model may need loading first. It passes the model adapter conformance suite.
- **`@mayurajs/storage-libsql`**, the first `@mayurajs` storage package: the Mayura store on libSQL (`createLibsqlStore({ url, authToken })` for Turso, a `sqld` server or a local `file:`, or `createLibsqlStore({ client })` with a `@libsql/client` client you own, which the store never closes), through the official `@libsql/client`. It uses SQLite's SQL and schema through `mayura/storage-sql/host`, so a local libSQL file and a `mayura/storage-sqlite` file are interchangeable, and it passes the same storage, memory and workflow conformance suites as SQLite and PostgreSQL on a local file (330 cases, including crash tests whose child processes are killed mid-transaction); its integration tests run the storage, memory and workflow suites against a `sqld` server given by `MAYURA_TEST_LIBSQL_URL`. Every operation is one write transaction, and a store runs them one at a time: the local driver waits for a file lock inside native code, blocking the event loop, so two of a process's transactions could otherwise deadlock. A local file locked by another process is retried for up to 5 seconds without blocking the event loop, and because the driver leaves a `BEGIN` that found the file locked unfinished on its pooled connection, which can then never commit, the store replaces its own client when that happens (a client you gave fails the call instead). The URL and token are options, never read from the environment; plain `http://` and `ws://` are accepted only for loopback addresses, and a token in the URL is refused. The storage conformance child fixtures gained a `libsql` adapter.
- **`@mayurajs/storage-mysql`**: the Mayura store on MySQL 8.0.19 or later (InnoDB), through `mysql2` (`createMysqlStore({ uri, tls, pool })`, or `createMysqlStore({ driver })` with a `mysql2/promise` pool you own, which the store never ends). The shared SQL layer (`mayura/storage-sql/host`) gains a `mysql` dialect: rows are locked with `FOR UPDATE`, work with no row to lock yet takes a named lock (`GET_LOCK`, released when the transaction ends), inserts that must not replace a row use `ON DUPLICATE KEY UPDATE` with the affected-row count, and updates read their rows back where PostgreSQL and SQLite use `RETURNING`; the SQL the SQLite and PostgreSQL adapters run is unchanged. The adapter translates table definitions (key columns become `VARBINARY(256)`, so identifiers compare byte by byte without padding; other text is `LONGTEXT` compared by code point), creates indexes MySQL cannot create conditionally, and runs every transaction at `READ COMMITTED` with a 5 second lock wait. A pool must not report found rows (`mysql2`'s default does): the store turns that off on its own pool and checks a pool you give. It passes the storage, memory and workflow conformance suites against MySQL 8.4 (345 cases, including crash tests whose child processes are killed mid-transaction); the conformance child fixtures gained a `mysql` adapter, and the row-lock ordering tests that ran only on PostgreSQL now also run on MySQL.
- **`@mayurajs/storage-mongodb`**, first release: aggregates (records, versions and events; what the server's submission journal and run records use), native memory and durable budgets on MongoDB, through the official `mongodb` driver (`createMongoStore({ uri, database })` or `createMongoStore({ client, database })` with a `MongoClient` you own, which the store never closes). It needs a replica set or sharded cluster: every write is one multi-document transaction with majority write concern, writers to the same document conflict, and the driver runs the losing transaction again. State and event data are stored as exact JSON text, so keys MongoDB restricts (`$set`, `a.b`) round-trip unchanged; memory ranks with BM25 in an aggregation pipeline; durable budgets use the SQL stores' own arithmetic, which `mayura/storage-sql/host` now exports (`initialDurableBudgetState`, `reduceDurableBudgetState`). It passes the aggregate, memory, durable-budget and basic durable-workflow conformance suites (116 cases), including crash tests whose child processes are stopped before a commit and killed; a crashed writer's open transaction holds its documents until the server aborts it (`transactionLifetimeLimitSeconds`, 60 s by default). It also runs the leased job scheduler (`store.scheduler`), on the server's clock, scheduled durable workflows (`store.workflows`, for `createScheduledWorkflowRuntime`), workflow graphs with their waits (`store.workflowGraphs`), execution waits (`store.executionWaits`), graph discovery (`store.workflowGraphDiscovery`, whose index is checked on initialization and refused if a same-named index differs) and workflow trees with their discovery (`store.workflowTrees`, `store.workflowTreeDiscovery`); durable budgets now use the same reducer as the SQL stores, through `DurableBudgetDatabase`. A run enrolled in scheduled execution changes only through its scheduled writer, as on the SQL stores. It passes every storage, memory and workflow conformance suite the SQL stores pass, including claims raced across independent stores, an approval that expires while it waits behind a held document, competing tree coordinators, discovery scans whose plans must use the index without an in-memory sort, and crash tests whose child processes are killed after a commit, or stopped just before one (353 cases in all).
- `mayura/storage-sql/host` exports the scheduler's persistence seam, so a store that does not speak SQL can run the same scheduler state machine: `SchedulerDatabase` now also takes a `SchedulerPersistence` (its `transaction(body)` gives a `SchedulerTransaction` of row reads and writes), with the row types `SchedulerJobRow`, `SchedulerHeldRow`, `SchedulerEventRow` and `SchedulerCandidateFilter`. `ScheduledWorkflowDatabase` likewise takes a `ScheduledPersistence` (a `ScheduledTransaction` adds the record, enrollment, link, wait-edge and completion rows to the scheduler's), with the row types `AggregateRow`, `WorkflowOwnerRow`, `WorkflowWaitTargetRow` and `CompletionRow`; `ExecutionWaitDatabase` takes an `ExecutionWaitPersistence` (`ExecutionWaitTransaction`, with `ExecutionStreamRow`, `ExecutionWaitRow`, `ExecutionWaitTargetRow` and `ExecutionWaitEventRow`); `DurableBudgetDatabase` takes a `DurableBudgetPersistence` (`DurableBudgetTransaction`, with `BudgetLedger`, `BudgetRootRow` and `BudgetEventRow`); and `WorkflowTreeDatabase` takes a `WorkflowTreePersistence` and the budget persistence (`WorkflowTreeTransaction`, with `WorkflowTreeMemberRow` and `WorkflowTreeJobRow`). The SQL stores run exactly the SQL they ran before. The workflow-tree tests became shared suites, which libSQL and MySQL now also pass.
- **Voice.** `mayura/voice` turns speech into text and text into speech through provider packages: `createVoices({ providers, prices, maxCallCostMicros })` gives every model an id `<provider>/<model>`, granted as `voice:<id>`, a price (`microsPerMinute` of audio for transcription, `microsPerMillionCharacters` for speech, from `prices` or, with `prices: 'catalog'`, a provider's dated catalog) and a per-call bound checked before anything is sent: speech is priced from its text, transcription from its audio's duration, which Mayura measures for WAV and you give for compressed audio. `transcriptionTool` and `speechTool` make tools that require `voice:<id>`, reserve the bound from the run's budget and report what each call cost. Failures are `VoiceProviderError`s with the model failure reasons and fixed messages. `mayura/testing` exports `voiceAdapterConformance` and `conformanceWav`. Documented in the new Voice guide.

- **Files.** `mayura/files` stores files by key in object stores. `createFileStore(backend, { maxFileBytes })` checks every key (`/`-separated paths, no `..`, at most 1,024 bytes), size, media type and metadata before a request is sent, and what the service returns before you see it. Every file has an `etag`: `put` takes `ifNoneMatch: '*'` (create only) and `ifMatch` (replace only that version), and a failed precondition is `CONFLICT`; a backend that cannot keep preconditions says so (`conditionalWrites`, `conditionalDelete`) and they are refused rather than ignored. `within(prefix)` is a view that cannot reach outside its prefix, for one tenant or run. `s3Files` is S3 and S3-compatible services (Cloudflare R2, MinIO, Backblaze B2) with its own SigV4 signing over fetch, so it runs on Node, Bun, Deno, Workers and Vercel Edge without the AWS SDK and reads nothing from the environment; `memoryFiles` is a backend for tests. `fileTools(store, { name })` gives agents read and list tools requiring `files:<name>:read`, and with `write: true` write and delete tools requiring `files:<name>:write`, which only create new files unless `overwrite` is set. Failures are `FileStoreError`s with fixed messages. `mayura/testing` exports `fileStoreConformance`. Documented in the new Files guide.
- **Artifacts in file stores.** `createArtifactStore({ files, maxArtifactBytes })` keeps artifacts in any file store that keeps preconditions (S3, R2 and the file storage packages) with every guarantee of the local store: content addressed by SHA-256, partitioned by scope, checked on every read, disclosed only under a policy, audited, reconciled (skipping files whose etag changed after planning) and backed up. References are identical to the local store's, so backups restore across the two. It is exported from `mayura/artifacts` and, without the local store, from the new edge-compatible `mayura/artifacts/files`. The local store's validation moved into shared code without changing its behaviour.
- **`@mayurajs/filestorage-gcs`**: Google Cloud Storage as a file store backend (`gcsFiles({ bucket, token })`), over the Cloud Storage JSON API with fetch and no dependencies, so it runs on edge runtimes. A file's etag is its generation, so `ifMatch`, `ifNoneMatch` and conditional deletes are Cloud Storage's own generation preconditions. Reads fetch the object's information and then that exact generation, retrying when the file is replaced in between, so bytes and information always describe one version; a conditional read is also checked against the generation it read. Credentials are an OAuth token source; `userProject` bills Requester Pays buckets; nothing is read from the environment. It passes the file store conformance suite.
- **`@mayurajs/filestorage-azure-blob`**: Azure Blob Storage as a file store backend (`azureBlobFiles({ account, container, accountKey })`, or a Microsoft Entra ID `token` source, or a `sas`), over the Blob REST API with fetch and no dependencies, signing requests with Shared Key itself. Files are block blobs written in one request; `ifMatch`, `ifNoneMatch` and conditional deletes are Azure's own conditional headers, and the etags listings give bare are quoted as headers give them, so the two compare. Metadata keys are stored under names Azure accepts (`run-id` as `m_run_id`) and read back as written. `endpoint` reaches Azurite. It passes the file store conformance suite against Azurite, which checks every signature.
- **`@mayurajs/filestorage-r2`**: Cloudflare R2 through a Workers binding as a file store backend (`r2Files({ bucket: env.FILES })`): the binding is the credential, with no keys, endpoints or signing, and it is typed structurally so no Workers types are needed. `ifMatch` and `ifNoneMatch` are R2's own preconditions (a precondition R2 answers with `null` is a `CONFLICT`); the binding cannot delete conditionally, so the store says so and refuses one. A read never touches the body stream before reading it, which claims it in the runtime. It passes the file store conformance suite on R2 in Miniflare (workerd).
- **`@mayurajs/filestorage-vercel-blob`**: a private Vercel Blob store as a file store backend (`vercelBlobFiles({ token })`), over fetch in the form `@vercel/blob` 2.8 sends (Blob API version 12) but without its dependencies or its environment variables, where `@vercel/blob` reads the API's address. `ifMatch` guards writes and deletes, `ifNoneMatch` makes a write create-only (a refused create-only write is a `CONFLICT` when the blob exists, whatever error the service gives), and reads bypass the CDN cache so they see the latest version. Vercel Blob keeps no custom metadata, so a write with metadata is refused. It passes the file store conformance suite except metadata, and a test runs `@vercel/blob` itself against the same local server to check the adapter sends the same requests.
- **`@mayurajs/filestorage-google-drive`**: one Google Drive folder as a file store backend (`googleDriveFiles({ token, folderId })`, or `folderId: 'appDataFolder'`), over the Drive API v3 with fetch and no dependencies, each file named by its key. Drive has no preconditions and does not keep names unique, so the store declares `conditionalWrites` and `conditionalDelete` false and refuses `ifMatch` and `ifNoneMatch`; reads take the newest of files a race left with one name, and a delete removes them all. Names are quoted and escaped in Drive queries. Drive cannot list by prefix or in key order, so a listing reads the folder (up to `maxFolderFiles`) and sorts it. Uploads are resumable at any size; deletes move files to the trash unless `permanentDelete` is set; metadata is kept as app properties of at most 124 bytes each. It passes the file store conformance suite (the precondition cases skip themselves) through an in-test Drive emulator.
- **`@mayurajs/filestorage-agentfs`**: an AgentFS filesystem (Turso's SQLite-backed filesystem for agents) as a file store backend (`agentFsFiles({ fs: agent.fs })`), typed by shape so any AgentFS build fits, Node, browser and Cloudflare Durable Objects. Each key is a path under `root`; a file's etag is the SHA-256 of its content, and its media type and metadata live in a sidecar file. With `singleWriter: true` (the store is the database's only writer) writes are serialized and preconditions are kept; otherwise they are refused. A key that needs a directory where another key is a file is refused, and deletes remove the directories they leave empty. It passes the file store conformance suite on AgentFS, both as the single writer and as one of many.
- **`@mayurajs/filestorage-files-sdk`**: any Files SDK provider as a file store backend (`filesSdkFiles({ files: new Files({ adapter }) })`), over its 40-odd adapters (Supabase, Netlify Blobs, Dropbox, OneDrive, Box, SFTP, WebDAV and more), with the client typed by shape. The store keeps what the adapter declares: preconditions only with native conditional create, replace and exact reads (and conditional deletes), metadata only where it is kept, and ranged reads where they exist (otherwise the file is read whole, within the limit). Files SDK errors map to the store's reasons without their messages. It passes the file store conformance suite over Files SDK's memory adapter, and through its own S3 implementation (the RustFS adapter over fetch) against RustFS.
- **`@mayurajs/filestorage-mesa`**: a Mesa repository (mesa.dev, a versioned filesystem for agents) as a file store backend (`mesaFiles({ token, org, repo })`), over its REST API with fetch and no dependencies. Each key is a file path on a bookmark, and every write or delete is a change committed on the bookmark's head; Mesa moves bookmarks only forward, so when another writer got there first the write is rebased onto the new head, and concurrent writers never lose each other's changes. Mesa has no per-file preconditions, media types or metadata: preconditions and metadata are refused, and reads report no media type. A file's etag is its git blob SHA; files are at most 128 KB (`mesaMaxFileBytes`), and ranges are read from the whole file. It passes the file store conformance suite through an in-test Mesa emulator.

## [1.0.0-rc.2] - 2026-09-29

### Added

- **Serverless functions are supported** on Vercel, and experimental on AWS Lambda and Google Cloud Run (Node.js 22 and 24); Vercel Cron and the Next.js route files are experimental too. The core is request-bound runs, workflows advanced by a scheduled `runOnce`, one-connection PostgreSQL pools and migrations from the pipeline. The Deployment guide has a section for each platform, and Supported platforms says so; edge runtimes are planned for 1.1. A new test runs every invocation as a fresh process stopped as soon as it answers: a request-bound run is readable by the next invocation, a background run cut off that way ends `outcome_unknown`, workflows finish through scheduled one-shot invocations with each effect once, and a step killed mid-effect is recovered without running it again. The same was checked live on a Vercel preview with Neon PostgreSQL through its pooled connection.
- **Request-bound agent runs.** `createAgentServer({ runExecution: 'request', runRecords })` (and the Node hosts) finishes each run, and records its outcome, before `POST /v1/runs` answers 202, so nothing runs after the response: for platforms that stop or freeze the process once it responds, such as serverless functions. The response and protocol are unchanged. The submission waits up to the agent's `limits.maxDurationMs` plus `requestTimeoutMs`; other routes keep `requestTimeoutMs`. It requires `runRecords` (`INVALID_CONFIG` otherwise).
- **PostgreSQL pool options.** `createPostgresStore({ pool: { max, connectionTimeoutMs, idleTimeoutMs } })`, with the previous values as defaults (8 connections, 5 s, 10 s), so serverless functions can use one or two connections per instance. `PostgresPoolOptions` is exported from `mayura/storage-postgres` and `mayura/storage`.
- **Run a worker once.** `mayura worker --once [--budget-ms <ms>]` advances everything due and exits, for scheduled jobs and functions; `WorkflowWorker.runOnce({ budgetMs })` does the same from code. It takes the leadership lease once (a standby returns at once), runs passes until every unit has completed a sweep or the budget ends, renews the lease between passes and stops if it is lost, then releases it. It reports `leader`, `completedSweep`, `held`, `passes` and `failures`; the CLI maps them to `succeeded`, `incomplete`, `standby`, `held` or `failed` (exit code 1). Units gain an optional `runOnce()`: lifecycle and composite hosts had it, and `coordinatorUnit` now has it. `runWorkerOnce` and `MayuraWorkerOnceReport` are exported from `mayura/cli`.
- Lifecycle and composite hosts keep their sweep position in storage, so a restarted worker, or the next `--once` run, continues the sweep where the last one stopped instead of revisiting the same runs first. A position that cannot be used starts the sweep over.
- **`z` from `mayura`.** The root import exports `z` (Zod 4), so a project needs no separate schema library: `npm install mayura` and `import { defineTool, z } from 'mayura'`. Zod 4.6.5 (MIT, no dependencies, no install scripts) is now a dependency of the package, reviewed like Hono and Clack. Any other Standard Schema validator still works, including a project's own copy of Zod; Mayura never checks where a schema comes from. `z` stays on Zod 4 for all of 1.x (see Versioning). The documentation, README, templates, starters and examples import `z` from `mayura`, templates and starters no longer install `zod`, and the assistant rules in `llms.txt` and generated `AGENTS.md` files say not to add it.
- Documentation: the Deployment guide covers every supported target, not only containers: a table to choose one, then Kubernetes manifests (migration Job, server and worker Deployments, probes, drain), managed container platforms (ECS on Fargate, Cloud Run, Azure Container Apps, Fly.io), process platforms (Heroku, Render, Railway), virtual machines with systemd, and mounting `createAgentServer` inside an existing Node.js app such as Next.js. It says plainly that serverless and edge runtimes are not supported yet, and why. A new example, `examples/embedded-handler.mjs`, runs the mounted handler end to end in CI.
- Documentation: a Credits page (`docs/project/credits.md`) naming the open-source projects and open standards Mayura is built on, what each one does in Mayura, and its license.

### Fixed

- Durable workflows settle a tool step abandoned by a stopped process on their own. A step that was `dispatching` when its process died (killed, evicted, or frozen past its limit) used to wait for someone to call `recoverAbandoned`. Now, once the tool's `timeoutMs` and a further minute have passed since the step's dispatch was recorded, the next process that advances the run settles it exactly as `recoverAbandoned` would: `unknown`, or `blocked` when its receipt shows the tool finished. It is never run again, and a step that a live process is still running is never touched. This covers lifecycle and format-2 workflows (and `agentStep`), records a `lifecycle.step.abandoned` or `step.abandoned` event, and needs no change to stored data. `recoverAbandoned` still does it at once.
- Release workflow: a release that stopped part-way, or one committed and tagged by hand, can be run again with its version, and every step skips what is already done (the version commit, the tag, the npm publish, the GitHub Release). `version.mjs set` does nothing when the code is already at that version. The commit's author and committer can differ (`RELEASE_GIT_AUTHOR_*`, `RELEASE_GIT_COMMITTER_*`).

### Fixed

- `anthropicMessages` refused every response from a Claude model that thinks before answering (such as `claude-sonnet-5`): its `thinking` block was an unknown block, so tool calls and some answers failed as unusable. The adapter now accepts `thinking` and `redacted_thinking` blocks (also when streaming), never releases them, and keeps each tool-call turn, signed thinking included, in the run's continuation to send it back unchanged, as Anthropic requires. Found by the live-provider check through Cloudflare AI Gateway.
- The cli-agent starter refused every file in a workspace named through a Windows short name (such as `C:\PROGRA~1`, or the temporary folder on CI runners): the workspace root and the requested file were resolved by different realpath functions. Both are now resolved the same way.
- A provider that refused a streamed call (a wrong key, a rate limit) was reported as an unusable response; it now fails for the provider's reason with its HTTP status, as a refused call does. A router that runs out of providers keeps the last provider's HTTP status. Found by the live-provider check.
- The support-agent starter could not use any real model provider: every model call failed before it was sent. Its `orders.list` tool takes no input, and the JSON Schema Zod writes for an empty object has no `required` list, which the provider adapters' strict check refused. Its `memory.recall` tool had an optional field, which strict schemas cannot express. The OpenAI, Anthropic and compatible adapters now accept an object with no properties and no `required` (and send `required: []`), `memory.recall` takes a nullable `query`, and the starter's tests hand every tool schema to both real adapters.
- `mayura workflow-get` (and the workflow cancel, pause, resume and signal commands) refused the server's view of a run whose tool step was waiting for approval, because the view includes the pending approval. The CLI now accepts it and shows the digest to pass to `workflow-approve --digest`; the approved tool call itself is checked but never printed.

- A release would have published `@mayura/cli` without its starters: staging copied only fixed folders, npm packs a folder matched by a `files` glob only with `/**`, and the archive check refused the starters' test folders. Staging now follows each package's `files`, the CLI's patterns are recursive, and the check verifies the starters are in the archive. Published packages now also name their repository, as npm provenance requires.

- `anthropicMessages` refused a tool-use response that also contained text, which Claude models often send before calling a tool. The text is now dropped and the tool calls are used; other block types are still refused.

- A lifecycle step refused for budget could stay pending when its write lost a race with a sibling step's write; it was then decided again only in a later wave, after the sibling may have released its reservation. The refusal is now re-decided on the latest state and always recorded while the budget is held.

Found by the research-team starter.
- The agent server never released finished runs or per-principal runtimes, so a long-running server answered `429` after `maxRuns` runs or `maxRuntimes` principals until restarted. Finished runs are now kept for `limits.runRetentionMs` (default 10 minutes); a run whose outcome was read may be released early under pressure; runtimes close when unused; and a same-key retry of a released run gets `410 RUN_EXPIRED` from a bounded tombstone instead of starting a second run.
- A strict TypeScript host could not pass `createWorkflowOperatorTransports` to the server: view node kinds, step statuses and fleet results were typed too loosely. They now use the server's record types, and `@mayura/server-node` re-exports `ServerIdentity`.
- A scheduled run whose approval expired before its step was admitted retried the refused preparation until it failed with a contention error. The driver now requests a fresh review, and the run waits for a human again.
- The migration planner could accept a settled tool step whose tool changed. The migrated state then failed validation. Such a plan is now refused, with the reason.
- CI on Linux and macOS:
  - The template check re-packed the native TypeScript compiler without its execute bit.
  - The SBOM script could not find a globally installed pnpm.
  - The Docker adapter tests used a Windows-only absolute path.
  - Two process-recovery tests could race a child that had already exited.

### Changed

- Models see each tool under its own id made safe for provider function names (`orders.list` becomes `orders_list`), instead of `tool_0`, `tool_1`, so instructions and skill catalogs that name tools match what the model sees.
- **Breaking (Code Mode):** the QuickJS sandbox enforces its limits for real: `memoryBytes` caps WebAssembly memory (it previously counted allocations and a program could grow to 2 GiB), `cpuMillis` counts only interpreter time and cannot be caught, deep recursion ends with a clean stack-overflow error instead of crashing the worker, the tool bridge can no longer be tampered with, and tool-call floods are bounded. The QuickJS worker runs under the Node.js permission model with an empty environment. Oversized or non-JSON results are `INVALID_OUTPUT` (they were `TOOL_FAILED`), CPU and memory overruns `LIMIT_EXCEEDED`. The adapters and promotion functions throw `MayuraError` instead of `TypeError`. Rebuild existing Docker sandbox images.
- **Breaking (errors):** `StorageError` extends `MayuraError`, so one type covers every public error. Its `code` is a general one (`STORAGE_UNAVAILABLE`, `INVALID_CONFIG`, `LIMIT_EXCEEDED`, `CONFLICT`); the exact storage condition is `storageCode` (check it with `isStorageError(error, code)`). A reused workflow idempotency key with different input, definition or settings says so instead of "storage version changed". Human request ids now include their run's index shard.
- **Breaking:** server error codes are specific: `UNAUTHORIZED` became `AUTH_REQUIRED` / `AUTH_INVALID` / `AUTH_EXPIRED`, `FORBIDDEN` became `CAPABILITY_REQUIRED`, `NOT_FOUND` became `ROUTE_NOT_FOUND`, `NOT_ENABLED` or a specific `*_NOT_FOUND`, `BODY_LIMIT` became `BODY_TOO_LARGE`, `RESPONSE_LIMIT` became `RESPONSE_TOO_LARGE`, `IDEMPOTENCY_REQUIRED` became `IDEMPOTENCY_KEY_REQUIRED`, and `ClientError.code` is the server's code instead of `HTTP_ERROR`. Unexpected server failures are 500 `INTERNAL_ERROR`, not 400. `GET /v1/runs/:id` returns exactly `{ id, status, budget, evidence, outcome? }` (the CLI's `run-get` and `run-wait` failed on the extra fields before).
- **Breaking:** `mayura/artifacts` scopes are Mayura's usual `{ principalId, projectId }` (both required) instead of `{ tenantId, projectId? }`. Stored artifacts stay reachable: the scope digest is unchanged for the same values.
- `mayura` with no command prints the help and exits 0 even when piped, and `mayura dev` runs a template project's `dist/index.js`.

- A `read` tool that throws, times out or is cancelled now ends as `failed` (or `cancelled`), not `outcome_unknown`: a read changes nothing outside, so there is nothing to reconcile. Its declared cost is still charged, and its evidence still records that the call's completion is unknown. Only `write` and `host` tools make an uncertain failure `outcome_unknown`.
- A budget that stops a call says which limit and by how much ("The call may cost up to 1000 micros, but only 0 of the budget's 0 micros are left"), and how to raise a budget of 0. A tool batch that does not fit names the run's `limits.maxCostMicros`.
- The package's optional peers accept later versions in the same major line (`better-sqlite3@^13.0.3`, `pg@^8.23.0`, QuickJS `^0.32.0`) instead of one exact version, so an existing compatible install is not a conflict.
- Calls that fail after the provider confirmed usage throw `ModelProviderError` with `costMicros` from the built-in adapters and the router, instead of `ModelInvocationError`; both are still accepted from custom adapters.

- Saga and loop statuses gain `paused`. Graph and tree discovery candidates can have status `paused`: coordinators skip them with the outcome reason `paused`, and `graphFleetTarget` and `treeFleetTarget` take `{ includePaused }` so inventories count them. Exhaustive switches over these unions need a `paused` case.
- `graphFleetTarget` and `treeFleetTarget` cap discovery pages at 32, the discovery bound. Larger inventory pages previously failed.
- Workflow migration ids are limited to letters, digits, `.`, `_` and `-`, so they are safe in URLs.
- Every workspace entry point is classified stable (47 application-facing plus 3 trusted-host entry points) against the 1.0.0 target. The package version changes at the release cut.
- The run event stream adds `step.started`, `step.completed`, `delegate.started` and `delegate.completed`; hook events accept all agent stages. Strict clients built on earlier previews must accept these event types.
- `MemoryEntry` includes the `superseded` state produced by native memory.
