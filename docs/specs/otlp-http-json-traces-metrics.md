# OTLP/HTTP JSON traces and metrics

Status: experimental optional metadata-only exporters. Deterministic protocol/unit and isolated packed-consumer evidence exist; collector/backend interoperability and semantic-quality evaluation remain open.

## Boundary

`@mayura/exporter-otlp` exports three independent factories for OTLP/HTTP JSON logs, traces and metrics. Each requires an explicit signal-specific endpoint, service identity, transport bounds and optional explicit headers. Imports and construction perform no network work. HTTPS is mandatory except for explicitly enabled literal `127.0.0.1`/`::1` development endpoints. No environment variables, ambient credentials, redirects, cookies, automatic discovery or retries are used.

The trace exporter accepts completed metadata-only spans with exact nonzero lowercase hexadecimal trace/span IDs, optional distinct parent ID, stable operation name, unsigned 64-bit decimal nanosecond boundaries, status, optional bounded run ID and optional attributes from a closed catalog (`OtlpSpanAttributeName`). A catalog attribute's value is either a bounded stable identifier (`[A-Za-z0-9][A-Za-z0-9._:/-]*`, at most 256 characters) or a non-negative safe integer; attributes are encoded in key order after `mayura.run.id`. It emits internal spans only. Free-form attribute keys, text values, events, links, exception text, prompts, messages, tool arguments/results and code are not part of this contract; one invalid span rejects its whole batch before transport.

The metric exporter accepts a fixed low-cardinality Mayura metric-name catalog, nonnegative finite values, unsigned 64-bit decimal times and optional bounded run/profile/status dimensions. Gauges cannot carry sum fields. Sums require a start time and explicit monotonicity and use cumulative aggregation. Points sharing a metric identity are grouped; one batch cannot change that identity's aggregation kind or monotonicity. User-defined names, labels and raw strings are rejected.

The wire format follows the stable [OTLP 1.11 protocol](https://opentelemetry.io/docs/specs/otlp/), including `/v1/traces` and `/v1/metrics`, lower-camel Protobuf JSON fields, decimal 64-bit values and signal-specific partial-success counts. Shapes follow the canonical [OpenTelemetry Protocol definitions](https://github.com/open-telemetry/opentelemetry-proto). This package deliberately implements `http/json`, not gRPC or binary Protobuf.

## Delivery semantics

Each exporter is single-flight and bounded by record count, encoded request bytes, streamed response bytes and deadline. HTTP 200 with an empty or bounded JSON response is success. `rejectedSpans` and `rejectedDataPoints` are validated against the sent count and accounted separately; partial success is never retried. Invalid counts, hostile/oversized bodies and non-200 responses fail with safe errors that do not reflect collector content.

Cancellation and close abort local waiting, but cannot prove that a collector did not receive a transmitted request. Inspection exposes immutable exact accepted/dropped/partial/failure/timeout/cancellation/byte counters and never endpoint headers. Telemetry remains optional and cannot authorize, block, cancel or change execution. Durable audit and compliance evidence require a separate mandatory persistence path.

## Workflow and agent trace projections

Two pure, versioned projections build spans for this exporter from already durable or already admitted metadata. Neither widens the privacy boundary: both emit only catalog attributes.

**Workflow runs** (`@mayura/workflows`: `workflowTraceSpans`, `workflowTraceContext`, `workflowStepTraceContext`, `createWorkflowTraceExport`). Input: a settled snapshot (status, per-step kind/status/receipt execution/child link, budget integers), the run's complete durable event log from sequence 1, and optionally its pinned definition (id, version, digest, node ids/kinds, tool id/version/declared cost). Output: one root span `workflow:<definitionId>` spanning the first to the last event, and one span `<kind>:<nodeId>` per step in the snapshot, from the step's first event carrying its `nodeId` to its last settling event (`step.completed|failed|blocked|skipped|output_blocked`, `human.responded|timed_out|invalid`, `timer.fired|invalid`, `workflow.wait_resolved`, `workflow.child_joined`, with the `lifecycle.` prefix removed), or the run's end when the step never settled on its own. Times are the store's event timestamps, clamped so that no span starts before the run or ends before it starts. The only event fields read are `type`, `sequence`, `createdAt`, `data.nodeId`, a fixed upper-case `data.code`/`data.reason` on failure events, and `data.childId` on `workflow.child_admitted`. Request/response/approval digests, human identities, inputs, outputs and messages are never read into spans.

- Identity: trace id = the first 32 hex digits of `digest('mayura:workflow-trace:v1', { runId })`; span id = the first 16 of `digest('mayura:workflow-span:v1', { runId, nodeId })` (`nodeId: null` for the root). An all-zero prefix is replaced by ending it in `1`. Projection is deterministic: the same log and snapshot always produce equal spans.
- Step context: every format invokes a step's tool with `callId` `<runId>/step:<nodeId>`; `workflowStepTraceContext(context)` returns that step's trace and span id, and refuses any other call id.
- Export: `createWorkflowTraceExport` keeps two kinds of durable records in the given aggregate store, scoped like the workflows (`digest('mayura:scope:v1', scope)`): an outbox of tracked run ids per `exportId` and a marker per (export, run) holding the last event sequence exported. `exportRun` exports a settled run only if its log is longer than its marker, sends batches through one serialized sink, and writes the marker only after every batch was accepted. `flush` visits the outbox round robin, removes exported, unchanged and unknown (`NOT_FOUND`) runs, and keeps unsettled and failed ones. Crash before the marker: the run is re-sent with identical ids. Crash after it: the next flush finds it unchanged. Invalid stored export state fails closed with `STORAGE_UNAVAILABLE`.
- Coverage: format 2, lifecycle (format 5), graphs (format 3) and workflow-tree roots (format 4; a child step is one span carrying `mayura.workflow.child.run.id`). Child-run internals, sagas and loops are not projected.

**Agent runs** (`@mayura/exporter-otlp`: `agentRunTraceSpans(events, { parent? })`). Every event is re-admitted through `snapshotRunEventMetadata`; rejected events are skipped. Output: `agent:<agentId>` for `run.started`..`run.completed`, `model.call` per paired primary start/completion (guardrail calls pair by `callId`), and `tool:<toolId>` per `tool.started`/`tool.completed` pair by `callId`; unpaired starts produce nothing. Ids use a 64-bit FNV-1a/SplitMix64 hash of the trace id, run id and call identity (no Node builtin), so re-projection is deterministic. With `parent`, the run span is its child and shares its trace, which nests an agent run under the workflow step that ran it.

## Limitations

This slice does not create spans automatically from live run events, propagate W3C context, sample, aggregate metrics across processes, retry within one export, export histograms/exemplars, adopt unstable GenAI semantic conventions or qualify a collector/backend. The workflow export's outbox is the only persisted queue, and it holds run ids, not spans. Backends that do not key spans by trace and span id show a re-exported run's spans twice with identical ids.
