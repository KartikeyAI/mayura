# Versioned durable workflow graph waits

Status: implemented and locally qualified on Windows x64 / Node 24.14.1. Extends [scheduled workflows](scheduled-workflows.md) and [completion facts](execution-completion-waits.md). This is a bounded development slice, not full durable child orchestration or enterprise qualification. Exact passing evidence, timing observations and remaining gates are in the [development ledger](../development-status.md).

## Public contract and scope

Add `@mayura/workflows/graphs` with `defineWorkflowGraph` and `createWorkflowGraphRuntime`. Graph definitions have the existing schemas, ID/version, result bindings and finite tool/join nodes, plus `{ kind: 'wait', id, dependsOn?, targets }`. `targets` is an existing literal or input binding, never a step-output binding. Its resolved value is an ordered array of 1–32 exact existing `ExecutionRef` values. The definition manifest explicitly includes `format: 3`; its digest uses `mayura:workflow:v2`. Persist state format 3 under owner profile 2 / public `scheduled-v2`. Format-2 definitions, hashes, validators, scheduled-v1 APIs and custom adapter contracts remain supported without widening their accepted formats.

The graph runtime offers submit, inspect, reference, events, runUntilSettled, approve, cancel, recoverExpired and close, with the existing scoped permissions, fixed-cost policy, limits and worker behavior. It does not offer attach. The optional driver-free `.workflowGraphs` storage capability supports the corresponding finite commands; existing `.workflows` accepts only v1. Use the same scoped submission identity and policy hash domains, so changing profile under an existing submission key conflicts rather than creating another effect.

All wait references resolve from validated immutable submission input or literal data before parent creation. Permit at most 128 target edges across a graph, at most 32 per wait, no duplicate run IDs within a wait and no self-reference. Target scope and policy must equal the parent. Targets may be existing scheduled-v1 or scheduled-v2 runs in the same configured backend. They cannot be future runs, unowned aggregates or missing references. Targets and bindings cannot change later. No format-3 attachment, automatic migration, step-derived references or API to add edges is provided. Consequently each legitimate edge points from a newly submitted parent to an already existing run; admission cannot introduce a dependency cycle. Privileged consistent database forgery is outside this guarantee.

When dependencies succeed, a wait becomes waiting without a handler, model call, executor permit, job, lease, cost reservation, resource hold or retained SQL transaction. A finite advance reads immutable terminal facts for all pinned references. Completion means any terminal outcome, not successful target execution. On all-terminal readiness the wait succeeds with the ordered metadata-only `ExecutionCompletion[]`; unknown, failed and cancelled target outcomes remain explicit. This output may feed normal downstream bindings, joins and final schema validation. Target outputs/receipts/secrets are not copied. Applications must explicitly drive the parent again; notification delivery and automatic background scanning are not part of this slice.

## State, ownership and integrity

State format 3 retains the common run and step fields of format 2, but explicitly permits wait steps. Wait statuses are pending, waiting, succeeded, failed (output admission limit) or skipped. Waits always have null receipt/approval/candidate and zero reserved cost; only succeeded waits contain output. Their admitted output must exactly match all pinned completion facts in order. Waiting/failed/succeeded waits require successful predecessors; a failed wait requires complete facts, and a terminal parent cannot retain an unresolved wait. Successful joins collect the exact ordered admitted predecessor outputs. Non-success terminal targets do not become successful tool receipts. Ordinary aggregate updates and standalone scheduler mutation remain fenced for either owner profile.

Add a parent-owned `mayura_workflow_wait_targets` table with scope, parent run ID, node ID, ordinal, target run/definition/policy identities. Its ordered immutable rows are inserted in the same transaction as parent creation/enrollment. Cross-check every bounded projection against immutable manifest + submission input on every load; missing, extra, reordered or mismatched targets fail closed. Check succeeded wait output against immutable completion facts and predecessor success. A wait cannot have a scheduler job. All transitions and canonical aggregate events commit together. There is no external WorkStream stream that can separately cancel or resolve a graph node.

Target preflight validation/materialization uses independent target-only transactions and finishes before the parent transaction. Parent creation rechecks target owner identities as immutable data without acquiring target aggregate/job/resource locks. Parent reads/control transitions retain the existing parent aggregate → jobs → resources lock order, then read its own target index and immutable facts. Target publishers never acquire parent or wait locks. Shared finite reducer and worker implementations support both profiles; do not copy an execution engine.

Repeated references share only an exact-identity, command-local target/fact lookup cache. Every parent index row is still validated, absent facts are re-read on the next command, and no mutable state or readiness observation is cached across transactions. Driver snapshots may skip redundant preparation reads for monotonically completed or already enrolled tool nodes; actual candidates retain fresh reads and authoritative compare-and-swap checks.

Immutable reuse is identity-based and privately owned: successfully decoded, detached and deeply frozen manifests can reuse their own validation; each driver compiles genuine registered definitions once; decoded driver views can reuse structural checks only after the runtime itself copied, froze and validated them. Scope/run/policy/profile checks still apply on reuse. Arbitrarily frozen caller objects, equal hashes, raw database rows, adapter replies and mutable reducer state never inherit this trust.

Preserve existing terminal publication in the central scheduled save path. Materialization fully validates either supported enrolled profile. Existing external completion joins may target either supported scheduled profile while retaining their exact reference/fact format. Old unsupported binaries fail closed on the new owner/state formats; mixed old/new writers are not qualified.

## Bounds, races and cancellation

Registration, entering waiting and resolving emit bounded metadata-only events. Unchanged repeated advance/recover calls consume no version, event, command journal, money or call budget. Wait outputs receive the existing per-output and aggregate limits. Aggregate size projection reserves worst-case room for every future wait observation as well as receipts, review identities and accounting, before admitting any earlier output. Reject an intrinsically oversized initial graph rather than creating a run that cannot later cancel or settle evidence.

Completion before/during parent creation either resolves the next advance immediately or leaves a durable ready predicate. Concurrent drivers serialize on the parent; only one can admit the wait output and prepare downstream effects. Retry after an uncertain submit uses identical submission content. Retry after uncertain advance observes the persisted state instead of replaying target or downstream work. Parent cancellation skips unresolved waits but never cancels targets or forgets already known target metadata. Terminal parent outcomes never resume after late target completion. Closing a driver leaves durable waits intact and closes no caller-owned store.

This does not spawn or own children, propagate cancellation to targets, share their budgets or authenticate a reference as a capability. Timers, any/quorum, future targets, dynamic branches/loops, durable workflow-as-tool execution, compensation, reconciliation and distributed notification/capacity remain separate work. No new external dependency, deployment, paid model call, publication or owner license decision is needed for this slice.

Custom adapters remain trusted persistence authorities. Public graph replies check structural/context identity, configured budgets and per-value output bounds. Driving with a registered graph additionally validates manifest/targets, join metadata and acknowledged submission input. Inspection without a definition cannot authenticate a full source graph or its facts. SQL tests cover specified redundant-state corruption, not every privileged event-row edit or an administrator consistently rewriting all copies; atomic history is a transaction guarantee, not cryptographic journal authentication.
