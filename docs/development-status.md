## Important boundaries

- Standalone scheduler claims do not automatically fence arbitrary aggregate writes. Explicit scheduled enrollment now atomically couples jobs, approvals and costs and blocks ordinary writers on owned runs. It accepts only new or pristine compatible format-2 runs; no automatic migration, policy replacement, durable children, built-in provider reconciliation, transactional outbox, timers, loops, compensation or fleet service is claimed. Unknown effects are never silently replayed.
- Ephemeral agent-child and workflow-as-tool composition remain process-local. The separate format-4 profile persists root-local tools, one-level owned child links, narrowed authority, approvals, accounting and joins, but it is not arbitrary durable workflow-as-tool composition or distributed capacity. External completion joins and format-3 graph suspension operate over independent scheduled runs and never propagate cancellation or budgets to those targets. Waiting inside an ordinary model/tool callback is not a supported nested-execution mechanism; use `agentAsTool`, explicit ephemeral `workflowAsTool`, or a format-4 tree at an application boundary. Parent budgets already include descendants and must not be summed with child snapshots.
- Standalone durable budgets preserve shared accounting across restarts but have no effect leases, grants, ownership links or dispatch. Their `host-v1` profile cannot be presented as scheduler-owned authority. Bounds are 128 accounts, depth 16, 128 bundles, 512 tickets and 2,048 events; lifecycle bounds preserve terminal evidence capacity. Unknown cost survives closure and retries. Ordinary reads validate state and journal continuity/tail, while event pages validate their requested payloads; this is not full historical replay or tamper-proof audit. Format 4 uses a separate fixed `workflow-tree-v1` table/owner and couples its reducer transitions to root/member execution in the same SQL transaction.
- Late handler completion may persist receipts after cancellation/close while the separately owned store remains open. It cannot rewrite the original result or release late output. Store/process loss can still leave unknown evidence.
- Signal WorkStream caps each stream at 256 signals, 128 waits and 1 MiB. The separate completion-wait capability has 128 lifetime waits per stream, 32 targets per wait and 257 journal entries, with explicit finite drains. Format-3 graphs allow 128 nodes, 128 total target edges and 32 targets per wait; target references cannot come from later step outputs or future runs. Finite discovery examines at most 32 ownership rows per page; a sweep includes retained terminal history and is not a stable snapshot or readiness promise. Registered continuation admits 1–32 definitions with at most 4 MiB cumulative manifest/resource metadata and one active page per coordinator; one driver shares local job capacity, while discovery/driver storage callback limits are separate and independent root money is not pooled. No notification driver, background polling or global retention service exists. Native memory caps each scope at 128 lifetime IDs (including tombstones) and 768 KiB. These are experimental correctness-first limits, not production-scale qualification.
- The scheduler bounds each job's retained attempts/evidence/commands and each query/batch, but has no global history-retention policy. Its resource identities are explicit, not inferred path aliases. Unresolved started work quarantines its resource holds; even successful receipt/cost reconciliation does not clear those holds without a separately qualified policy. Fences are not provider-side exactly-once guarantees. Redundant-state checks detect covered corruption, not a privileged database writer consistently rewriting every copy.
- Memory deletion removes canonical content/provenance and current retrieval results. WAL, database pages, backups, previous exports/disclosures require separate erasure/retention controls.
- Context needs a trusted current-source manifest and faithful validity/provenance mapping. Stale caller evidence is not magically refreshed. Token estimates are not exact provider tokenization. There is no context cache or model compaction yet.
- PII recognizers are heuristic. Literal checks are not semantic injection defenses. Batch-local checking cannot catch every protected span split across batches; whole-response safety requires whole-response buffering.
- Auxiliary models require application-owned destination screening, genuine shared accounting and exact grants. The older caller-wired helpers do not obtain runtime authority. The separate managed definition API now binds ephemeral moderation to actual accounts/counters/permits; it does not automatically provision language helpers or durable checks. Model verdicts and translations may be wrong; low-confidence preservation is not permission to bypass mandatory downstream checks. Protected segments stay local only when the application classifies them correctly.
- Required hooks are control-only and run after relevant prior guard barriers; they cannot reverse a denial, rewrite tool inputs, receive tool results for another decision, or grant capabilities. Allowed read/pure actions still use the owning runtime broker. A final-agent hook inspects a candidate before the required-child join. Optional observers, other stages, transforms, write/host actions, nested model/child requests and durable delivery remain separate work. In-process callbacks are trusted JavaScript, not a sandbox.
- HTTP history and idempotency are in memory, finite and never silently evicted. Replacement loses that history; no restart-safe command deduplication is claimed. Stream expiry requires reauthentication, but revocation is not continuously checked midstream. The Node host is loopback-only; TLS, reverse proxies, distributed quotas, durable worker serving and UI rendering remain separate work.
- Workflows, WorkStream and memory depend on driver-free storage contracts, so custom adapter or ephemeral workflow consumers install neither SQL driver. Selected `@mayura/storage-sqlite` and `@mayura/storage-postgres` installations contain only the chosen driver; the `@mayura/storage` compatibility facade intentionally installs both. The declared development-preview installation matrix is in [the support matrix](support-matrix.md). The shared SQL host entry is trusted integration plumbing, not an authorization boundary.
- MCP admission, bounded durable workflow phases, explicit OTLP export, dependency-free headless UI state and optional React hooks are implemented. Hosted memory/context integrations, production-qualified hostile-code execution, rendered UI components and production starter deployments remain outside the finite release-gate claims. The native observer is optional process-local telemetry, not required durable audit. Application-provided source/sink callbacks are trusted JavaScript, not hard-isolated code.
